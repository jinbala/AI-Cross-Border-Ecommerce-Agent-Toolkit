# 两个选品项目的合并评估

评估日期：2026-10-17。基于两个本地项目的源码、数据格式和已有测试，不涉及真实账号登录或店铺操作。

## 结论

可以合并，适合做成一个“服装生意工作台”。建议采用裤装项目的桌面外壳和罗盘选品入口，接入跨境工具箱已有的产品档案、利润测算、AI 工作流和业务试验记录。

两个项目的互补点是“找到可研究的款”和“验证工厂能否做、以什么价格做、如何小规模试卖”。这能减少准备表格、重复导入和在两个软件之间复制资料的操作，但不会自动证明某款在另一个平台也能盈利。

本文件记录合并前的评估。经确认后已在当前仓库实现 2.0 整合版，实施结果见 [2.0 更新说明](./09_Desktop_v2.0_Release_Notes.md)。原 `product-selection-specialist-skill-1` 目录保持不变，所需源码引入当前仓库并保留出处与许可证。

## 项目分工

| 项目 | 已有能力 | 合并后建议保留 |
|---|---|---|
| `AI-Cross-Border-Ecommerce-Agent-Toolkit` | Python / Tk 桌面版；产品档案；供货与零售利润测算；七类 AI 工作流；8 类参考筛选；SQLite、备份和业务试验 | 财务计算、工作流、档案与业务记录作为后续经营环节 |
| `product-selection-specialist-skill-1` | C# / WinForms / WebView2 桌面版；HTML / JS 清单；罗盘账号页；类目、周期、价位查询和翻页；收藏、筛选和导出 | 统一桌面外壳、罗盘找款、收藏和榜单更新 |

第二个项目虽然名称中有 `skill`，但当前源码已经包含独立桌面客户端。其 JavaScript 在构建时打包进页面，桌面端日常使用不需要 Node.js。开发构建仍需对应工具和 WebView2 SDK。

## 建议的实际操作流程

1. 在同一个软件中登录罗盘，读取当前账号有权限查看的裤装榜单。
2. 按男裤 / 女裤、款型、价格筛选，把感兴趣的款加入统一候选清单。
3. 选中候选，建立本厂产品档案；商品名称、链接、来源类目和统计周期自动带入。
4. 补充本厂成本、面料、交期与对应渠道的真实费用，分别计算供货或零售报价。
5. 按需生成市场复核、商品文案、图片制作方案或视频脚本。
6. 建立小批量测款记录，记录实际支出、收入和下一步动作。

建议导航：选品找款、我的候选、产品档案、报价与利润、AI 工作流、测款记录、账号与设置。原有市场分析、成果和备份能力可放入对应页面，避免单纯叠加两套菜单。

## 需要处理的实际衔接

### 界面与后台

两边使用不同的界面技术，直接复制文件不会成为一个软件。建议保留 C# / WebView2 作为主窗口，复用裤装项目现有的网页清单；将当前 Python 财务、工作流和存储逻辑保留为本地后台模块，并提供固定的 JSON 命令接口。Python 随安装包提供，最终用户不需要自行安装开发环境。

这比同时保留两套主窗口更符合“一次打开、连续操作”的目标。第一阶段可以先验证数据桥接，完整界面统一放在后续阶段。

### 数据格式与来源

裤装项目的原始输入是 `meta + products` 或 `relations`；客户端缓存为 `pants-desktop-collection-v1`，同时保存 `snapshots` 和 `data`。当前桌面版的候选则包含 `strategy`、`status`、`evidence`、`checks` 等字段，存储在 SQLite 中。需要新增转换层。

- 商品 ID 保留为文本，使用平台与商品 ID 标识候选；不同周期、类目和查询价位保留为来源观察记录，不能互相覆盖。
- 保留来源账号标识、统计起止日期、类目、查询价位、榜内排名和实际采集范围；相同商品在不同价位榜的名次不是同一榜单排名。
- 罗盘价格带不是已核实的最低 SKU 价，也不是工厂供货价；不能直接填进利润计算的收入字段。
- 罗盘成交件数、支付金额和转化率以原始区间展示。近 7 天成交区间不能直接映射成当前筛选器的精确“月销量”，也不能取区间中点充当真实数值。
- 抖音需求只作为其他渠道的调研线索。目标市场、Temu 供货结算、运输、售后和平台费用另行核实。
- 继续区分演示数据、真实快照和缺失数据；不能把未采集或更新失败当成零销量。

### 收藏与旧数据

裤装收藏按账号存于 WebView2 的本地存储，采集缓存位于用户本机应用数据目录；当前工作台使用独立的 SQLite 数据目录。迁移时应先备份，再合并候选、收藏和来源记录，并校验数量及重复项。现有登录配置单独保留，不将浏览器登录数据混进业务备份。

### 文档与能力口径

裤装项目的部分 Skill / 适配器说明仍描述“没有无人值守翻页”，而桌面源码 `CompassUpdater.cs` 已有按类目、价位和页码读取的逻辑。合并时应分清独立脚本与桌面宿主各自具备的能力，统一说明。

已保存的真实试采只有两个类目首页共 20 条的范围说明，不能因代码支持翻页就宣称已实测所有类目或完整 TOP200。当前评估没有重新验证真实账号权限或平台页面。

两个项目的本地许可证均标为 MIT；复用代码时保留各自的版权声明和许可证。构建时不带入真实采集文件、收藏、密钥、登录配置和个人运行缓存。

## 建议实施顺序与验收

| 阶段 | 交付 | 验收重点 |
|---|---|---|
| 1. 打通数据 | 罗盘候选可进入经营工作台 | 不重复填表；长 ID 不丢精度；来源、区间和周期不丢失；重复导入不重复新增 |
| 2. 统一桌面 | 一个入口、一个主窗口，接入档案和报价 | 收藏后能直接算成本、建档；保留现有收藏和缓存；无需自行安装 Python / Node.js |
| 3. 串联经营 | 候选可交给 AI 复核并建立测款记录 | 资料自动带入；渠道与费用分别核算；记录可追溯 |
| 4. 完整验收 | 旧数据迁移、备份恢复、打包程序检查 | 失败不覆盖旧数据；离线可看已保存清单；真实账号采集单独验证 |

不建议第一步同时扩大到全部服装类目、所有跨境平台和自动上架。先打通目前已有的裤装来源，验证实际省事后再扩大范围。
